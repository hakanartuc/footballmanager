# Faz 0B — Flutter App Skeleton Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A portrait Flutter app (iOS, Android, macOS for dev) that hosts the Faz 0A engine inside an isolate and lets a player start a new game, press "Devam" through seasons, set a lineup, see results, the table, fixtures and the inbox, and save/load — in Turkish and English — with widget, golden and integration tests and a device performance gate.

**Architecture:** `apps/cm_app` depends on `packages/engine` by path. The engine runs in a dedicated isolate behind an `EngineGateway` interface; the UI never touches `World`. The isolate answers with small immutable snapshots built by pure functions (`SnapshotBuilder`) that also power an in-process gateway used by widget tests. A single `GameController` (ChangeNotifier) owns the game state machine; screens are thin. Saves go through the engine's `SaveStore` (file-backed via `path_provider`), with a rotating autosave. Localization is ARB-based; event-to-text mapping lives in one place.

**Tech Stack:** Flutter 3.44 / Dart 3.12, `provider`, `path_provider`, `shared_preferences`, `intl` + `flutter_localizations` (gen-l10n), `integration_test`, `golden_toolkit`-free plain `matchesGoldenFile`. Engine package `engine` (path dependency).

**Spec:** `docs/superpowers/specs/2026-10-20-cm-simulation-design.md` — Bölüm 2 (simetri, çift dil), 3 (gün döngüsü), 10 (dikey bilgi mimarisi), 11 (Faz 0 kapsamı), 12 (Flutter yapısı, isolate, web/masaüstü kuralları), 14-1/2/3 (gün üç parçada; kayıt gün sınırında; hızlı modda AI yönetir), 16.12 (oyun başlangıcı, kayıt yuvaları, şema sürümleme, rehber), 17 (test katmanları), 18.3 (kayıt düzeni), 19 (yetki). Faz 0A plan and engine README: `docs/superpowers/plans/2026-10-20-faz0a-engine.md`, `packages/engine/README.md`.

## Global Constraints

- App code never imports `World` mutation paths; all engine access goes through `EngineGateway` (Spec §12: engine separate; isolate hosting).
- Engine runs in its own isolate in the real app (`IsolateGateway`); widget tests use `InProcessGateway` over the same `SnapshotBuilder` (Spec §12).
- Portrait phone layout; no hard-coded pixel widths; every screen renders at 360×780 and 390×844 without overflow (Spec §12 web/desktop rule 1).
- Storage behind `SaveStore`; the app never touches file paths outside `AppSaveStore` (Spec §12 rule 2). No mobile-only plugin in the core (rule 3).
- Turkish and English from the first screen; all UI text from ARB files; engine events rendered through one `EventText` mapper; no string literals in widgets except test keys (Spec §2, §16.12).
- Save slots 1–5 manual; 6–8 autosave rotation (newest first); autosave after every advance (Spec §16.12: otomatik kayıt, son 3 döndürülür).
- Schema versioning: this phase bumps the engine save schema to **2** (inbox message ids) with a registered migration 1→2 (Spec §16.12).
- Entitlement stub: `Entitlements` decides allowed `WorldSize`s; development build allows all (Spec §19).
- Performance gates (device/simulator, profile mode): a "Devam" that advances to the next match on a **large** world shows no frame > 100 ms on the main isolate; save < 2 s; new game (large) < 10 s end-to-end including isolate spawn (Spec §3, §18).
- Determinism untouched: the app passes commands through; it never reads `DateTime.now()` into game state (Spec §2).
- Commit per task; conventional commits; Fable trailer for Fable commits (Opus commits carry the Opus trailer).
- Model per task tagged `[Model: Fable]` / `[Model: Opus]` per Spec §11.1; Fable reviews every task.

## Review Focus

1. **App killed mid-advance** (OS kill while the isolate is simulating): on next launch the newest autosave must load and the game must continue from a day boundary, never from a half-day. Pinned in Task 5 (repository autosave only after an outcome) and Task 16 (restart test).
2. **Load of a save from a newer app** (schema 3 file into a schema-2 app): the UI must show a readable error and keep the slot intact, not crash. Pinned in Task 13.
3. **Unemployed manager**: every screen must render without a club (Home shows the unemployed state, Squad/League show pickers, "Devam" still works). Pinned in Tasks 9, 10, 11.
4. **Lineup with suspended/injured players chosen by the user**: the editor must refuse to submit and say why, using the engine's `validateLineup` errors. Pinned in Task 10.
5. **Locale switch mid-game**: every visible string, including inbox items already rendered, re-renders in the new language; no cached text. Pinned in Tasks 6 and 12.

### Task 4: IsolateGateway `[Model: Fable]`

**Files:**
- Create: `lib/engine/isolate_protocol.dart`, `lib/engine/isolate_gateway.dart`; test `test/engine/isolate_gateway_test.dart`.

**Interfaces:**
- Produces: `class IsolateGateway implements EngineGateway { static Future<IsolateGateway> spawn(); }`. Protocol: `sealed class EngineRequest { int id; }` with one subclass per gateway method carrying its arguments; `sealed class EngineResponse { int id; }` → `Ok(Object? value)` | `Fail(GatewayErrorKind kind, String message)`. Worker: `_worker(SendPort)` creates a `ReceivePort`, sends its `SendPort` back, holds one `InProcessGateway`, dispatches requests sequentially (a request queue; the UI awaits each future). Errors in the worker are caught per request and returned as `Fail`; the worker never dies on a game error. `dispose()` sends `Shutdown`, kills the isolate.
- Uncaught worker error (bug) → the pending future completes with `GatewayError(engine, stack)` and the gateway marks itself broken (`isBroken`), subsequent calls throw `GatewayError(engine, 'isolate crashed')`.
